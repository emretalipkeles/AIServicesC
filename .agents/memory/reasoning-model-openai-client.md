---
name: gpt-5.6-terra reasoning model constraints on the OpenAI (Azure) client path
description: Non-obvious Azure behavior for reasoning-effort deployments — read before touching the OpenAI client path or any call site using ModelId.gpt54()/gpt54High()/defaultOpenAI().
---

Confirmed live against the gpt-5.6-terra deployment (2026-08-26): Azure rejects any non-default `temperature` **outright**, independent of whether `reasoning_effort` is set at all — this is stricter than the older gpt-5.4 behavior, which only rejected `temperature` once `reasoning_effort` was present. There is no request shape on this deployment that accepts a real temperature value; Bedrock is unaffected and continues to honor `temperature` normally.

`reasoning_effort` accepts `'none' | 'low' | 'medium' | 'high' | 'xhigh'` on this deployment (`'minimal'` is rejected, unlike some other reasoning-model families). `'none'` is the one value confirmed to spend zero reasoning tokens — it behaves like a classic non-reasoning model. `'low'/'medium'/'high'/'xhigh'` all draw reasoning tokens from the same completion-token budget as visible output, so a budget sized for a plain reply can still be silently exhausted by reasoning overhead before any output is produced; keep checking `finish_reason === 'length'` explicitly rather than treating a short/empty result as "nothing found".

**The old `temperature: 0` "opt out of reasoning" pattern is now expressed as `reasoning_effort: 'none'`.** OpenAIResponsesClient (`server/src/infrastructure/ai/OpenAIResponsesClient.ts`) keeps the `ChatOptions.temperature` field as the caller-facing "I need deterministic, literal output" signal, but internally maps any explicit `temperature` to `reasoning_effort: 'none'` instead of forwarding the value (which would 400). Any code that talks to Azure directly (bypassing `IAIClient`, e.g. via a raw `AzureOpenAI` SDK client) must do this translation itself — `AIDelayEventExtractorWithTools.ts` was one such case that had to be fixed directly.

**Function tools + `reasoning_effort` don't mix on `/v1/chat/completions`.** Attaching `tools` to a chat-completions request while passing any `reasoning_effort` other than `'none'` is rejected outright ("Function tools with reasoning_effort are not supported ... use /v1/responses or set reasoning_effort to 'none'"). The only way to get real reasoning depth (e.g. `'medium'`) with tools attached is to move that call to the `/v1/responses` endpoint instead, which supports `tools` + non-`'none'` reasoning together and is confirmed live to return valid strict-`json_schema` output while doing so. Both `OpenAIToolUseClient.ts` and `AIDelayEventExtractorWithTools.ts` use this endpoint for exactly that reason — a call site still on Chat Completions with `tools` attached is a signal it's stuck at `reasoning_effort: 'none'` and should probably migrate too.

**Chat Completions vs. Responses API shapes are not drop-in compatible** when migrating a tool-calling call site: tools go from nested `{ type, function: { name, parameters } }` to flat `{ type, name, parameters }`; `response_format: { json_schema }` becomes `text: { format: { type: 'json_schema', name, schema, strict } }`; `max_completion_tokens` becomes `max_output_tokens`; usage fields become `input_tokens`/`output_tokens` instead of `prompt_tokens`/`completion_tokens`; truncation is `response.incomplete_details?.reason === 'max_output_tokens'` instead of `finish_reason === 'length'`; and multi-turn tool loops feed the model's own `response.output` items straight back into the next `input` array (plus a `function_call_output` item per tool result) rather than building a chat-style `messages` array with `role: 'assistant'/'tool'`.
